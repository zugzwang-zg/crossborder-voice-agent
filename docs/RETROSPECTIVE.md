# 项目复盘

## 目标回顾

项目最初希望把双语评论从“情感分类结果”推进为“可以回到证据、可以交给负责人继续验证的运营洞察”。v0.2.0 已完成方法链路和公开原型，但尚未验证真实业务采用与增长结果。

## 已完成的结果

- 对 1,000 条英语/西语评论完成确定性分层分析；
- 形成 15 条带支持量、分母、语言分布、限制和原文证据的洞察；
- 在 100 条冻结测试集上完成 Baseline v1 与 Improved v9 对比；
- 属性 Precision 从 72.22% 提升到 83.18%，属性 F1 从 67.47% 提升到 74.02%；
- 人工证据语义有效率从 88% 提升到 96%（每版本抽查 25 条）；
- 交付无需 API Key 的公开 Dashboard 和可复现离线流程；
- 建立 118 个 Python 测试、4 个 Dashboard 测试、资产/许可审计与多角色 AI 预评审流程。

## 做对了什么

### 1. 把“可追溯”设为输出契约

项目没有把生成式摘要直接当成洞察，而是要求标签、支持量和原文证据保持关联。这让 Dashboard 能从聚合结论返回记录，也让错误分析有具体对象。

### 2. 用冻结评测约束提示词迭代

Baseline 与 Improved 使用相同模型和测试集，避免用更换输入掩盖退化。评测同时报告 Macro-F1、逐类指标与样本限制，没有只挑 Accuracy。

### 3. 把产品边界写进界面和文档

历史数据、缺少商品标识、分层样本和未校准 confidence 都会影响业务解释。将这些限制前置，比在报告末尾添加免责声明更能降低误用。

### 4. 把个人项目的审查过程做成可复现流程

多模型 AI 预评审不能替代人类评测，但可以检查结构、证据拟合、范围越界和风险措辞。哈希、角色和运行范围使其比一次性聊天审阅更可追踪。

## 哪些地方走了弯路

### 标签扩张过快

早期版本希望一次覆盖太多属性和语用现象，导致边界重叠。后续通过白名单、冲突规则和更保守的提示提高 Precision。教训是先从业务动作需要的最小标签集开始，再用错误分析决定扩展。

### 把模型 confidence 当成展示指标

平均 confidence 看起来容易理解，但未校准时会制造虚假精确感。v0.2.0 已移除聚合平均值，改为显示支持量、分母、证据和限制。

### 产品材料曾落后于实现

旧项目简报仍写 Streamlit，README 的测试数量也未随版本更新。发布链路应把作品集文档视为产品界面的一部分，并加入版本复核清单。

### AI 评审复用需要完整上下文校验

只比较候选哈希不足以安全复用仲裁结果；主评审上下文变化也可能使旧仲裁失效。运行器随后增加角色、模型、提示和完整上下文校验，并隔离范围外结果。

## 如果重新开始

1. 先用 20—30 条真实任务样本定义行动分类和验收标准；
2. 在开发模型前记录人工整理基线，包括耗时、覆盖率和一致性；
3. 从第一版就区分“已测模型指标、产品可用性指标、业务结果指标”；
4. 为文档中的版本号、测试数和关键指标增加自动一致性检查；
5. 更早邀请目标岗位从业者完成可用性走查，而不仅是检查模型输出。

## 下一阶段计划

| 优先级 | 工作 | 验证问题 |
|---|---|---|
| P0 | 完成 40 条挑战输入的双人独立标注与仲裁 | 模型在长评论、混合情感和隐含属性上是否稳定？ |
| P0 | 设计人工 vs AI 辅助的同批耗时对照 | 产品是否真的减少整理时间？代价是什么？ |
| P1 | 接入带商品、站点和时间字段的近期合规数据 | 能否支持单品复盘与时间趋势，而不越界外推？ |
| P1 | 邀请 3—5 名目标用户完成任务走查 | 筛选、证据回查和行动路由是否符合真实工作流？ |
| P2 | 增加反馈汇总与洞察采用状态 | 哪类建议被接受、驳回或需要更多证据？ |

## 简历表述边界

可以表述：独立完成产品定义、双语文本分析原型、评测体系、证据看板和发布审查；在冻结测试集上取得已报告的模型指标改进。

不应表述：已经提升真实 GMV、转化率或运营效率；已经过专家评审；可以代表当前市场或特定国家消费者；已经达到生产级 SLA。
